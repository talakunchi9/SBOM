1. Summary and Target Hierarchy

--- TABLE START ---
In plain words: the business thinks in four levels: an organisation owns applications, an application is made of modules, and each module uses packages. The current database already has this shape, but with different table names. The plan is to rename the tables, add a few columns, and add four validation checks, in small safe steps.

In plain words: the business thinks in four levels: an organisation owns applications, an application is made of modules, and each module uses packages. The current database already has this shape, but with different table names. The plan is to rename the tables, add a few columns, and add four validation checks, in small safe steps.

3. Target Database Schema
In plain words: ten tables. Organisations own applications and repositories. Applications contain modules and are linked to repositories. Each scan produces one SBOM; an SBOM holds components and findings; findings point to a shared vulnerability list and can be overridden by triage.
Figure 2: Target database diagram (PK = primary key, FK = link to another table)

Gate 1: Format check (SG-04)
What it checks: whether an uploaded file is an SBOM at all. Allowed: CycloneDX JSON (1.3 to 1.6) and SPDX JSON (2.x).
Step by step:
The user uploads a file and chooses the input type "SBOM Document".
The system tries to read the file as JSON. If that fails, stop with INVALID_​JSON.
The system checks the top level is an object (curly braces). If not, stop with INVALID_​STRUCTURE.
The system looks for CycloneDX signs: bomFormat equal to CycloneDX, or components together with a specVersion or metadata. If found, it checks the version is supported; if not, stop with UNSUPPORTED_​VERSION.
If it is not CycloneDX, the system looks for SPDX signs: spdxVersion, or packages together with an SPDXID. The version must start with SPDX-2; otherwise stop with UNSUPPORTED_​VERSION.
If it is neither, stop with INVALID_​SBOM_​FORMAT and the message "Uploaded file must be a valid CycloneDX or SPDX JSON document."
If it passed, remember the format and version (for example CycloneDX 1.5) and go to Gate 2.

Gate 2: Required fields (SG-06)
What it checks: that every component has a name and a version.
Step by step:
The system goes through the components one by one and reads the name, and the version (or versionInfo in SPDX).
If the name is blank, record an error for that row: "Component name is mandatory and cannot be blank."

Gate 3: Package URL (purl) (SG-07)
What it checks: that each package URL follows the official format pkg:type/​namespace/​name@version?qualifiers#subpath.
Step by step:
The text must start with pkg:. If not, it is invalid.
Next comes the type (for example npm, maven, pypi). It must start with a letter and may contain letters, digits, ., +, - and _.
Then an optional namespace and a required name, separated by /. A missing name is invalid.
Then, optionally, @version, ?qualifiers and #subpath.
Special characters must be percent-encoded. For example the @ in a scoped npm name is written %40 (pkg:npm/%40angular/​core@14.​0.​0).
If any purl is invalid, flag it (warning) or reject the upload, as decided for the project; the message names the bad purl. Otherwise go to Gate 4.

Gate 4: Duplicate check (SC-25)
What it checks: that the same application is not registered twice, and that duplicates in a bulk file are caught.
Step by step:
Rules: in one organisation no two applications share a name (ignoring upper and lower case). In one application no two modules share a name or path. In a bulk file, a repeated pair of repository URL and branch is a duplicate.
When a user creates an application by hand: remove spaces around the name. If it is empty, stop with INVALID_​NAME (400).
Look for an existing application with the same name in the same organisation. If one exists, stop with DUPLICATE_​APPLICATION (409): "Application 'Core-Banking-System' already exists in this organization."
If none exists, create the application: new ID, next readable code such as APP-0042, save the owners, and show it to the user (201).
In a bulk file, do the same check for each row. A duplicate row is flagged DUPLICATE_​PROJECT and skipped; the other rows continue.

Why it needs checking
1
Purl with a raw @ (for example pkg:npm/@angular/​core@14.​2.​0)
I ran the pattern from the plan: it rejects this purl, because the namespace cannot start with @. Only the percent-encoded form (%40angular) passes. The plan’s own "valid purl" test list contains the raw form, so that test would fail. Decide whether to accept raw @ or fix the test list.
2
Permissive mode in Gate 2
The rules say the version becomes "Version unknown" and the NTIA flag is false, but the sample code does nothing when strict mode is off. That behaviour still has to be built.
3
Supported CycloneDX versions
The sample code accepts 1.2 to 1.6, but the message and rules say 1.3 to 1.6. Pick one.
4
Test coverage
The test file has no test for the duplicate gate or the bulk duplicate rule.
5
Export Center "Working"
The classification table says the Export Center is wired to the API. The earlier validation found it builds its own files in the browser. Priority 1 fixes this; treat it as not working until then.
6
Checksum fix wording
Priority 1 says to fix SPDX SHA-256 to 64 hex characters. The real cause is the npm sha512- base64 text labelled SHA-256: decode it to hex and label it SHA-512.
7
Default scanner name in migration 009
The migration defaults scanner_​name to Antigravity-Scanner and 1.​5.​0. The existing scanner reports bom-engine and sbom-engine-1.​0.​0. Choose the real values.

Helper functions in the sample code

Case-insensitive names

Counts
